# Download metadata documentation

## Status

- Proposed feature / change request
- Scope: Download artifacts from speeches, KWIC, word trends, and n-gram workflows
- Goal: Give users a consistent, human-readable record of the data and selections behind each download.

## Summary

Keep `manifest.json` as the machine-oriented record of each download. Add human-readable metadata generated by the backend from the same request and configured data provenance. Embed it without wrapping JSONL or CSV downloads in an outer ZIP file.

## Problem

Download manifests are built separately by multiple ticket services. Their fields differ, and some omit corpus or metadata versions. Filters use internal ids such as party and gender ids, which are not suitable for documenting a search in research notes or publications.

The previous frontend-generated `metadata.txt` was readable but cannot reliably cover the current asynchronous and format-specific download workflows.

## Scope

- Produce a consistent human-readable description of selections, query settings, data versions, sources, and download origin.
- Resolve selected people, parties, genders, and chambers to display labels.
- Preserve explicit start and end years in every description, including an unfiltered full corpus range.
- Include search text when the originating tool has one; omit it for filter-only speech downloads.
- Carry equivalent metadata in ZIP, JSONL gzip, and CSV gzip downloads.
- Configure repository and frontend links rather than hardcode them.

## Non-Goals

- Redesign the public query API.
- Make manifests a complete query replay mechanism.
- Change the existing primary data rows or speech text payload.
- Standardize every endpoint-specific field currently stored in `manifest.json`.

## Current Behavior

Ticket services independently create manifest dictionaries. The download service adds corpus and metadata versions in some ZIP download paths, while archive paths do not consistently add both versions. The ZIP writer can include `manifest.json`; JSONL gzip and CSV gzip writers currently ignore the supplied manifest because those formats are single compressed files.

## Proposed Design

### Canonical metadata model

Create a shared backend builder for a download metadata model. The model is the source for all format-specific renderings and includes:

- Selected speakers, parties, genders, and chambers as display labels.
- Explicit `from_year` and `to_year` values, defaulting to the corpus start and end years when absent from the request.
- Search text and tool-specific settings when applicable, such as KWIC context, lemmatization, cut-off, or aggregation settings.
- Corpus version and metadata version.
- Configured links to the SWERIK records and persons repositories.
- Configured frontend 

The builder receives the raw filters and optional tool-specific query fields. It resolves party, gender, chamber, and person identifiers through the existing corpus metadata/codecs. Empty categorical filters are rendered as `Alla`.

The builder must not mutate or replace the raw-code manifest data. It may be used by the existing manifest builders to guarantee common provenance fields, but endpoint-specific raw fields can remain as they are.

### Human-readable rendering

Render the canonical model as a stable Swedish text representation. The core lines follow the previous user-facing convention:

```text
Valda talare: Alla
Valda partier: Centerpartiet, Liberalerna
Valda kön: Man
Valda kammare: Första kammaren, Andra kammaren
Årsintervall: 2007 - 2022
Sökord: klimat
Data-version: SWERIK-records 1.4.1, SWERIK-persons 1.1.3
SWERIK-records: https://github.com/swerik-project/riksdagen-records
SWERIK-persons: https://github.com/swerik-project/riksdagen-persons
Nedladdat från: https://riksdagsdebatter.se
```

Optional lines are included only where meaningful. In particular, filter-only speech downloads do not contain `Sökord`.

### Format-specific delivery

- ZIP: add `metadata.txt` alongside the existing `manifest.json` and data entries.
- JSONL gzip: write one leading JSON object with `record_type: "metadata"`; all speech objects have `record_type: "speech"`. Consumers filter on the record type.
- CSV gzip: write `##`-prefixed metadata lines before the CSV header. Consumers using pandas can pass `comment="#"` when reading the file.

This retains the current extensions and content types. No outer archive is introduced for JSONL gzip or CSV gzip.

### Configuration

Add a small provenance section to `config/config.yml`, mirrored in `tests/config.yml` and `config/debug.config.yml`. It supplies the records repository URL and public frontend URL. Continue deriving the persons repository link from the existing `metadata.github` configuration, or move both repository URLs into the new section if that yields a clearer symmetric layout.

## Risks And Tradeoffs

- CSV comment lines are valid text but are not part of the CSV table. Consumers that do not support comment prefixes must skip them before parsing.
- JSONL consumers must handle the initial metadata record rather than assume every line is a speech. A discriminator prevents ambiguity.
- Display labels must be resolved against the metadata version used for the result. Missing or retired ids need a predictable fallback such as the raw id or `Okänd` rather than failing a completed download.
- ZIP-based download tests that assert exact member lists will need updating. CSV and JSONL tests must verify their respective metadata encodings and unchanged speech payloads.

## Testing And Validation

- Unit-test metadata resolution for selected and unselected values, including person ids, parties, genders, chambers, and explicit full-range years.
- Unit-test Swedish text rendering and conditional tool-specific lines.
- Test every writer: ZIP contains `manifest.json` and `metadata.txt`; JSONL starts with a metadata record; CSV starts with comment lines and remains readable with `comment="#"`.
- Exercise one download per applicable router and verify corpus version, metadata version, configured source links, and selected labels.
- Confirm that missing metadata mappings degrade gracefully and do not block a download.

## Acceptance Criteria

- Every supported download format contains user-readable metadata without changing its external file format or adding an outer ZIP.
- The metadata names every selected categorical filter rather than exposing only internal ids.
- Each download documents explicit start and end years, corpus version, metadata version, repository provenance, frontend origin, and timestamp.
- Search and tool-specific settings appear only when relevant to the originating request.
- Existing raw `manifest.json` data remains available for consumers that use it.

## Recommended Delivery Order

1. Add provenance configuration and the canonical metadata builder with resolution and rendering tests.
2. Add `metadata.txt` to direct and ticketed ZIP download paths.
3. Add JSONL metadata records and CSV comment preambles, with format-specific reader tests.
4. Add the missing common provenance fields to archive manifests where practical.

## Final Recommendation

Implement backend-generated, human-readable download metadata from a shared canonical model. Keep `manifest.json` as the raw machine-oriented companion record, and serialize the readable model according to the download format.
