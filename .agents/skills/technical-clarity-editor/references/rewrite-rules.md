# Rewrite Rules

Use these rules when lightly revising a document to improve clarity without changing its technical level, tone, or intent.

The audience may include developers, technical project members, domain experts, and AI coding agents that use the document as implementation or review context. The goal is to make the document easier to follow, not to make it informal or beginner-oriented.

* Prefer minimal edits over full rewrites.
* Keep the original terminology when it is accurate and used consistently.
* Do not replace precise technical terms with simpler words unless the original wording is unclear.
* Preserve the document’s register: proposals should still sound like proposals, design documents should still sound like design documents, and technical notes should still sound technical.
* Do not normalize the whole document into a new writing style.
* Improve sentences that are hard to parse, overly long, repetitive, or vague.
* Keep clear sentences unchanged, even if they could be made simpler.
* Use shorter sentences only when they improve readability.
* Do not make the prose choppy or conversational unless the source already has that tone.
* Keep useful nuance, qualifications, and tradeoffs.
* Explain technical terms only when the original document is unclear or when the term is central to understanding the section.
* Preserve code blocks, YAML, paths, identifiers, names, examples, headings, and section order.
* Do not add new requirements, opinions, assumptions, examples, or implementation details.

When editing, use the smallest change that solves the readability problem.
If a paragraph is already clear, leave it mostly unchanged.
If a term is precise but potentially unfamiliar, prefer keeping the term and improving the surrounding explanation.
